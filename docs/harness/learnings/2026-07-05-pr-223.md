> **要約(5行以内)**: 対象PR https://github.com/subroh0508/pokeform/pull/223 / commit 3da46fb6679a / merge 2026-07-05T08:57:05Z / 差分 3 files +120/-71。pokeapi-names / showdown-sync / serebii-bulletin の PR 自動作成を third-party（peter-evans/create-pull-request）から `gh pr create`（GITHUB_TOKEN）へ置換。撤去 test-branch からの E2E dispatch で全ステップ緑 + PR 自動作成を実測（P1〜P4 の end-to-end 実証）。

## ✅ Keep（継続したいこと）

- **E2E を実 dispatch で確認した**: 撤去 test-branch から `pokeapi-names.yml` を dispatch し、fetch→sync→generate→check→verify→gh pr create の全ステップ緑 + PR 自動作成を GitHub Actions 上で実測（run 28735319793）。「コードが正しい」でなく「CI で通る」を証拠化した。
- **E2E が repo 設定ブロッカーを発見した**: `gh pr create` が `can_approve_pull_request_reviews: false`（"Allow GitHub Actions to create and approve pull requests" OFF）で失敗。これは cpr でも同じ制約で、過去の cpr は cherry-pick で手前失敗し露見していなかった潜在問題。E2E がなければ設定ブロッカーは merge 後まで隠れていた。
- **差分ガードの落とし穴を E2E 前に自己発見・修正した**: `git diff --quiet` は untracked（from-scratch で削除→再作成された languages）を検出しないため、`git switch → add -A → git diff --cached --quiet` の順へ修正。E2E で「languages は main と byte-identical（差分なし）だが workflow 差分あり → PR 作成」を実測し guard の正しさを確認。
- **label 事前作成で既知 gap を解消**: `gh pr create --label` は label を自動作成しない（cpr は自動作成）ため `gh label create --force` を前置。PR #219 で実測した `data:names not found` を恒久解消。
- **workaround を捨てて根本修正へ切り替えた**: 復元 PR #219（seed + ローカル等価）を close し、機構修正（Phase 1）+ 非 third-party 化（Phase 2）で「クリーンな取得フロー」を通した。
- **3 workflow を同一パターンで統一置換**し、body は heredoc→`--body-file`、`${{ }}` は Actions 事前展開、`git push --no-verify` で pre-push hook の redundant verify を回避、と一貫した。

## ⚠️ Problem（詰まった点・制約）

- **PR 作成が repo 設定に依存する導線が無かった**: 設定 OFF だと `git push` は通る（`permissions: contents: write`）が `gh pr create` のみ失敗する（GraphQL: not permitted to create PRs）。事前チェックが無く E2E で初めて顕在化。cpr でも同じ依存だったが誰も明文化していなかった。
- **GITHUB_TOKEN 作成 PR は `on:pull_request` CI を自動トリガしない**（GH 仕様・cpr でも同じ・非回帰）。auto-merge ゲート（CI 緑必須）に影響するが、workflow 内 verify が事前ゲートとして機能する前提。この制約は理解しておく必要がある。
- **3 workflow で gh pr create ボイラープレート（~25 行）が重複**。composite action 化も可能だが workflow 間のロジック共有は可読性とのトレードオフで見送り（4 本目が出たら再検討）。
- **repo 設定変更は不可逆・セキュリティ関与**ゆえユーザー承認を要した（Actions が PR を作成できる = 権限拡大）。自動化の前提が repo administration に食い込む。
