## ⚠️ Problem（詰まった点・制約）

- **1 つの plan PR 内で設計が 4 回転回し、その都度 renumber が発生**した（静的 skill → +全件辞書 phase → update-catalog を author-static-data へ再定義 → Phase 6 を基盤/投入に分割）。planning doc は WIP とはいえ、対話ドリブンの再設計を 1 PR に畳み込むと renumber コスト（ファイル rename + cross-plan 参照張り替え）が累積する。
- **設計確定までに長い Q&A を要した**（「PokeAPI は何を取るか」「languages を誰が作るか」「bijection ゲートは何を強制するか」「scaffold は誰が担うか」）。これらは `plans-new` の OVERVIEW 段階でデータフロー前提として洗い出せていれば、PR 途中での手戻り・renumber を減らせた性質の論点だった。
- **当初ゴール「data 完全削除から自動復元」が設計途中で部分的に崩れた**。`rules.yaml` / `type-specs.yaml` を「どの skill も触らない静的コミット」に決めた結果、完全削除時に自動復元されないファイルが残った。ゴールとスコープのトレードオフが会話後半で顕在化した（前提の洗い出し不足）。
- **renumber を手作業 sed で 3 回繰り返した**。番号張り替えは機械的だが件数が多く、毎回取りこぼしリスクがあった（検証で実害は防げたが、作業自体が反復的）。
- **`AskUserQuestion` が初回に拒否され**、以降プロンプトでの確認に切り替えた。選択肢提示の粒度/タイミングがユーザー期待とずれ、方針確認の往復が増えた。
